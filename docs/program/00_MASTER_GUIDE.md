## The one-paragraph picture
The site is a static GitHub Pages directory of Hanceville and Cullman County: 723 listings, 723 profile main pages plus 1,965 profile tab pages, 66 category pages, 60 story pages, and section pages, all in the theme black, purple, and white (Wallace State content in orange, blue, and white). The listing records live in `data.js` (moved out of the homepage in PR #51); the homepage (`index.html`) carries the presentation and loads them. Most profile and category pages are generated by `tools/build_places.py`. Shared behavior lives in `app.js`; the Facebook embed loader is `place.js`. Quality is gated by Lighthouse CI on every pull request. The program is worked under the standard by Big Dog, expanded into specialist cells on 2026-11-03 when Charles removed Maggie from the website team structure and moved her duties into the Big Dog Research and Development cell (see BIG_DOG_EXPANDED_STRUCTURE_2026-11-03.md), together with Grok and Copilot, and nothing publishes without Charles approving the named package.

## Sources of truth (one per fact, never two)
- **Listing facts** (names, addresses, phones, websites, Facebook links, logos, descriptions in English and Spanish, hours text): the records in `data.js` (`window.SLH_LISTINGS`), mirrored for people in `listings_master.csv` in this folder. If the two disagree, live `data.js` is right and the CSV is regenerated.
- **Businesses page data**: `businesses.json` (the page renders from it; fixing `businesses.html` alone does not fix the cards).
- **Profile page content**: generated; the truth is the generator inputs. A hand patch to a generated page is allowed only inside an approved release and must be logged in `releases_log.csv`, or the next regeneration will silently overwrite it.
- **The standard**: `Charles_Development_Standard.txt`. Changes only at Charles's direction, versioned, and reissued to all bots in the same pass.
- **Program state**: this folder. If it is not in the registries, it is not current state; check the live site before believing anything else, including older master files. The local master HTML is stale (734 listings, synced through PR #28) and is an archive, not a source; since the WS1-A records pass it sits at `~/workspace/your_files/archive/Shop_Local_Hanceville_MASTER_through_PR28_stale.html`.

## Handoff protocol (how any bot picks up another bot's work)
1. **Claim before you build.** Add or update your row in `workstreams.csv` (workstream, owner, status, staging location, date) before starting. If a workstream already has an owner, coordinate through the registry and the goal files; never run a second copy of the same work.
2. **Stage, never edit live.** All work is built in a named staging package in the workspace (a folder with the files plus a `RELEASE_SUMMARY.md` or `STAGING_SUMMARY.md` stating the base fingerprint, every change, what was deliberately not changed, and the stop rule). The live site and the repo's main branch are only ever changed by publishing an approved package.
3. **Base check and stop rule.** Before staging, fetch the current live files and fingerprint them. Build on that base. Before publishing, check the base again; if it moved, stop and rebuild. Never force a release onto a moved base.
4. **One change, one home.** A fix that belongs everywhere goes in the generator (`tools/build_places.py`) or in shared code (`app.js`, one file), not in hundreds of hand edits. If you hand-patch generated files in a release, log it so the generator owner can fold it in.
5. **Maker and checker are different.** Whoever built a package does not solely validate it. Big Dog independently re-checks releases against the live site, record by record, whatever bot built them.
6. **Renames and removals have a blast radius.** Changing a listing's name or removing it touches: the homepage record, its profile family, tiles and prev/next links on other listings' related pages, category pages, `places.html`, `sources.html`, `sitemap.xml`, and any data JSON that carries it. Search the whole repo for the name and its web address before calling the change complete (PR #44 and #45 are the worked example).
7. **Facts only.** No invented phones, addresses, hours, logos, dates, or coordinates. A field with no verified source stays honestly blank, and a status like "closed" is recorded only where the source says so. Every fact carries its source and the date checked.
8. **Verify by rendering, not by bytes.** A release is verified only when the published page is rendered and its working parts are exercised (grid renders, search filters, rails fill, no console errors). Byte-identical delivery proved nothing on 2026-11-03: PR #44 shipped exactly the staged file, and that file carried a runtime error that emptied the homepage grid, because helper functions removed as duplicates in one script block were still called there while their kept copies lived in another block's private scope. Rule: functions with the same name in different script blocks are NOT duplicates unless one block provably never runs; before removing any "duplicate", render the page and exercise it.
9. **After publishing, verify live and log it.** Re-fetch the live result, confirm the change as a visitor sees it, then update `releases_log.csv`, `features_registry.csv`, `listings_master.csv`, and `workstreams.csv` in the same pass. A release that is not logged did not happen, as far as the next bot is concerned.

## Conflict and duplicate prevention rules
- Never create a second file, page, or record for something that already exists; search first (the repo, the sitemap, `listings_master.csv`). Duplicate listings are defects (a duplicate Hanceville Drug stub was removed in PR #41).
- Never edit a file another workstream has claimed in `workstreams.csv` without handing off through the registry.
- Branch names carry the date and the package name (example: `combined-fixes-2026-11-03-a`). One pull request per named package. Merge once; never re-merge or duplicate a PR to fix a title.
- Cache versions: pages load `app.js?v=16`. When shared code changes must reach visitors immediately, the release raises the version in the pages it touches and notes it in the summary.
- The never-link list is absolute (hijacked, parked, and spam domains, kept in the standard's working files and both bot instruction files). A domain that starts returning spam goes on the list and comes off every page in one release.
- The site email `shoplocalhanceville@gmail.com` stays off the site until Charles confirms the account is fixed; contact routes to Facebook Page messages. Do not re-add it in any template, generator, or form.
