# Detail Prevention and Visual Detection Protocol — Expanded Big Dog

Set by Charles Adams on 2026-11-03. Purpose: catch small detail issues before they reach Charles or a visitor, discover imperfections and upgrade candidates by looking at the work, and turn every finding into a fix or a development written in raw code. This protocol binds every cell. A package that has not passed it is not presented.

## Part 1 — Detail prevention

1. Exact object rule. Before acting, name the exact object the instruction refers to: the file, the page, the element, the image, or the surface. A still image and an animated feature are different objects. A listing card and its profile page are different objects. When Charles sends a picture or a screenshot, the object is what the picture shows, and the work starts from that picture.
2. Look before answering. Open the image, the file, or the rendered page and look at it. Never describe, judge, or promise work on something that has not actually been viewed in this pass.
3. Name accuracy. Copy every name exactly as written: people, businesses, pages, and Big Dog himself. A similar word is a wrong word. Names in a finished package are checked letter by letter against their sources.
4. Small detail checklist, run on every package before it is presented: spelling and wording, labels and tab names, counts, dates, phone numbers, theme colors against the black, purple, and white standard, logo correctness, profile fields complete, and Spanish parity wherever the surface carries Spanish.
5. Correction loop. When Charles corrects a detail, the correction is written into the program masters in the same pass, so the same mistake cannot be made twice. The correction names what it replaces.

## Part 2 — Visual detection

1. Render and capture. Every staged package is rendered and screenshotted at phone, tablet, and desktop widths before presentation. Validation inspects the screenshots themselves, in addition to the automated gates. A check that never looked at the page does not count as a visual check.
2. Imperfection scan list. Uneven card heights in a row. Pale or faint logos and artwork that vanishes on its background. White bars or any color that drifts from the theme. Overlapping, clipped, or truncated text. Images stretched, squashed, or cropped in a way that loses integrity. Blank frames and broken embeds. Misaligned tabs and inconsistent spacing. Dull, mismatched, or low quality imagery. Contrast that fails a visitor with low vision.
3. Findings handling. Every imperfection found is entered in the prevention register with its screenshot, page, width, and severity. A fixable imperfection becomes a brief on the standard template and is fixed in raw HTML, CSS, or JavaScript only. Nothing visual is patched with a workaround that hides the symptom and leaves the cause.
4. Upgrade candidates. Anything that works but could be better is logged separately as an upgrade candidate, with a screenshot and a one paragraph case, and is batched for Charles's decision list. Upgrades never ride along silently inside a fix package.
5. Before and after proof. Every visual fix keeps its before and after screenshots with the package record, at the same widths, so the improvement is proven by looking, not by claim.
6. Cadence. A visual pass runs on every staged package, after any theme or layout change, and as a full site sweep monthly. Findings feed the brief queue in priority order: visitor facing breakage first, imperfections second, upgrade candidates third.

## Closing rule

The point of detection is development. Every issue this protocol finds ends in one of three recorded states: fixed in raw code and proven by screenshot, held for Charles with the evidence attached, or logged as an upgrade candidate with its case written. An issue that is only mentioned is not handled.
